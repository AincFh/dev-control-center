# ATLAS · 研究蓝图 → 研发工作包

## 能力边界

该链路只在静态 GitHub Pages 中通过浏览器事件把 **42 类研发蓝图** 转为 **5 个可编辑、可导出、可设置依赖的本地工作包**。它不会调用后台 Agent，也不会读取 GitHub Token、写入远端 Issue、验证许可证或自动标记产品交付。

## 使用流程

1. 打开 ATLAS 的「GitHub 星图」，定位「从开源研究到真实产品」。
2. 选择研发领域；可填写上游公开仓库 owner/repo（仅作为研究来源）。点击「生成具体方案」。
3. 在「目标自有仓库」选择当前 AincFh 公共仓库；列表只来自账号公开仓库快照（默认允许 ATLAS 本身 dev-control-center）。
4. 点击「加入执行工作台 · 5 阶段」，ATLAS 转到「执行工作台」，自动产生 5 个按序依赖的本地工作包。
5. 调整人工估算单位、负责人、优先级与截止日期；使用已有容量规划，必要时独立打开各工作包的 GitHub Issue 草稿人工提交。
6. 导出工作包 JSON，供跨浏览器恢复。所有进度只存在当前浏览器，本功能不声称跨设备自动同步。

## 阶段和默认人工估算

| 阶段 | 默认工作量单位 | 首次导入阶段 |
| --- | ---: | --- |
| 上游来源与许可审查 | 2 | 待规划 |
| 可运行技术验证 | 4 | 待规划 |
| 产品功能实施 | 12 | 待规划 |
| 质量与安全验收 | 6 | 待规划 |
| 交付与维护 | 4 | 待规划 |

这些数字只作为**人工规划的初始估算**，与 Codex、ChatGPT、云算力或实际工时没有直接对应关系。

## 设计与数据安全

- 上游 owner/repo 永远不能当作工作包目标仓库。目标仓库必须在自有仓库选择器中。
- 生成 ID 根据类别、目标仓库和上游来源确定；重复导入保留人工修改，额外内容仅追加。
- 生成完整五阶段链路后再进行容量与依赖检查，失败不会写入部分任务。
- 生成的工作包包含「蓝图批次」来源标识；若遇到不一致的 ID，不覆盖既有记录。
- 现有工作台上限 500 个工作包，依赖环和不存在的上游阶段会拒绝导入。
- 「导入成功」仅表示浏览器本地任务规划已生成；不代表技术验证、许可审查、构建、部署或人工验收。
- 页面使用文本 DOM API，来源字符串不插入 innerHTML；源码与第三方研究条目不会自动复制进自有仓库。

## 验收

运行 npm test：tests/blueprint-execution.test.js 覆盖五阶段依赖、重复导入、人工数据保留、来源差异、输入合法性、冲突拒绝、容量上限以及坏图拒绝。
站点构建还必须通过 scripts/verify-dist.mjs 检查并打包 blueprint-execution-core.js。

验证网页行为：切换多个领域和来源，生成蓝图 → 选择目标仓库 → 导入 → 查看工作台五个工作包 → 修改一个任务 → 返回重复导入 → 确认没有重复且修改依旧存在。之后分别在桌面、手机视口、深色模式和 reduced-motion 环境检查布局与键盘可用性。
